# CimBar v2.1 — rateless repair frames and payload compression

Status: Approved design, awaiting implementation plan
Date: 2026-09-18
Builds on: `docs/superpowers/specs/2026-09-17-cimbar-v2-format-design.md` (v2, implemented in release v0.9.1)

## 1. Problem

Transmitting a 700 KB file is 345 frames of 2104 bytes. The display loops
them in a fixed order every 69 s (200 ms/frame) while the phone decodes one
frame in 240–450 ms, so it catches roughly every second displayed frame.
Two effects make the last frames take longest:

- **Aliasing.** The decode period is close to a multiple of the frame period,
  so the receiver samples the same phase of the loop and keeps missing the
  same frames.
- **Coupon collecting.** Even with random misses, collecting all N specific
  frames when each display is caught with probability p takes about
  N·ln(N)/p frame slots: ~4000 slots (13 min) for N=345, p=0.5, almost all of
  it waiting for one or two particular frames.

v2.1 removes both: any N linearly independent frames reconstruct the file,
so no specific frame is ever awaited, and files shrink before they are cut
into frames.

## 2. Scope and compatibility

- Frame geometry, finders, tiles, cell packing and the RS(255,191) layer are
  unchanged. The header version byte stays `0x02`.
- Two new header flag bits (§3). v2 decoders (v0.9.1) reject a frame whose
  flags carry unknown bits with reason `flags`, and `FrameAssembler` skips
  rejected frames, so a v2 decoder still assembles an **uncompressed** v2.1
  file from its source frames and refuses a compressed one with that reason.
  There is no attempt to decode v2.1 repair frames with v2 software.
- Both apps ship v2.1 in the same release. The web app produces only v2.1;
  both apps decode v2 and v2.1.
- Constants live in `spec/cimbar-v2.json` (§10) and are mirrored into
  `web-app/format-data.js` by the existing generator.

## 3. Frame header

Unchanged layout: `[ver 0x02][flags][fileId u16][seq u16][total u16]`.

| flags bit | name | meaning |
|---|---|---|
| 0 | encrypted | payload is AES-256-GCM (unchanged) |
| 1 | repair | this frame is a repair frame; `seq` is the repair id r |
| 2 | compressed | the container is zlib-deflated (§4) |
| 3–7 | reserved | must be 0; a decoder rejects the frame (`flags`) |

- `total` = N, the number of **source** frames, on every frame including
  repair frames.
- Source frame: bit 1 clear, `seq` = i ∈ [0, N).
- Repair frame: bit 1 set, `seq` = r ∈ [0, 65536). A repair frame is
  meaningful only together with `fileId` and `total`.
- Bits 0 and 2 are identical on every frame of a file; a frame whose bits 0/2
  disagree with the assembler's first accepted frame is rejected (`flags`).

## 4. Payload pipeline and compression

Encoder:

```
file bytes ──► container = [u32 nameLen][name][file]          (unchanged)
           ──► if zlib(container) is ≤ 95 % of container: deflate, set bit 2
           ──► optional AES-256-GCM (bit 0)                     (unchanged)
           ──► u32 length prefix + zero padding to a multiple of 2104
           ──► split into N source frames of 2104 body bytes
```

Decoder (both apps, in `decodeFramedPayload` and its JS twin):

```
bodies ──► strip length prefix ──► decrypt if bit 0 ──► inflate if bit 2 ──► parse container
```

- Compression happens **before** encryption; ciphertext does not compress.
- Format: zlib (RFC 1950 framing around RFC 1951 deflate). Browser:
  `CompressionStream('deflate')` / `DecompressionStream('deflate')`; Dart:
  `ZLibCodec()`; Node tests: `zlib.deflateSync/inflateSync`. Level is the
  platform default; the format is what interoperates, not the level.
- Threshold 5 %: below that saving the file is sent uncompressed (bit 2
  clear), so already-compressed media costs nothing extra.
- N is computed after compression and encryption.

## 5. Coding layer: systematic random linear coding over GF(256)

### 5.1 Field

GF(256) with primitive polynomial `0x11D` — the field the RS code already
uses; both codebases have the exp/log tables (`web-app/rs.js`,
`android/lib/core/services/galois_field.dart`). Addition is XOR.

### 5.2 Rows

Let body_i (i < N) be the 2104-byte body of source frame i (the bytes after
the 8-byte header, before RS encoding). Every frame carries a row
(coefficients c ∈ GF(256)^N, body ∈ bytes^2104):

- source frame i: c = e_i (unit vector), body = body_i;
- repair frame r: c = coef(fileId, r) (§5.3), body = Σ_j c_j · body_j.

Repair bodies are 2104 bytes like source bodies; they carry no length
information of their own. Any N linearly independent rows determine all
body_i.

### 5.3 Coefficient generation

Coefficients are derived from the header alone so the receiver never needs
side information:

```
state = ((fileId & 0xFFFF) << 16 | (r & 0xFFFF)) XOR 0x9E3779B9   (uint32)
if state == 0: state = 0x9E3779B9
xorshift32(s): s ^= s << 13; s ^= s >> 17; s ^= s << 5     (all mod 2^32)
discard two outputs (warm-up)
c_j = low 8 bits of the j-th subsequent output, j = 0..N-1
```

Test vectors (first 12 coefficients):

| fileId | r | c_0..c_11 |
|---|---|---|
| 0x1234 | 0 | 105, 41, 69, 131, 204, 147, 100, 57, 131, 69, 213, 104 |
| 0x1234 | 1 | 172, 102, 148, 83, 214, 33, 65, 77, 72, 114, 95, 198 |
| 0x0000 | 0 | 58, 181, 31, 55, 208, 191, 57, 184, 238, 180, 211, 60 |
| 0xFFFF | 65535 | 121, 111, 142, 219, 96, 68, 203, 183, 1, 72, 231, 148 |

These vectors are stored in `spec/cimbar-v2.json` and asserted by the JS and
Dart test suites. An all-zero coefficient row (probability 256^−N) is never
transmitted: the encoder skips that r.

### 5.4 Limits

- Coding requires N ≤ `coding.maxFrames` = 4096 (8.6 MB after compression).
  Larger files are encoded as v2 (no repair frames, bit 1 never set) with a
  warning in the UI; compression still applies.
- Dense elimination costs about N·(N + 2104) byte operations per received
  row: ~1 M at N=345, ~25 M at N=4096 (tens of milliseconds on a phone).
  Memory: pivot rows N × (N + 2104) bytes — 25 MB at the cap.

## 6. Transmission

### 6.1 Present mode (web app)

Present mode no longer loops the GIF. It draws frames on a full-screen
canvas at the selected delay:

1. one systematic pass: source frames 0 … N−1 in order;
2. then repair frames r = 0, 1, 2, … without end (wrapping at 65536).

Each repair body is computed when needed (N × 2104 GF multiply-adds, a few
milliseconds at N=345), RS-encoded and rendered with the existing
`encodeRSFrame`/`renderFrame`. The page shows "source pass" / "repair frames
streaming" and the current r. Pressing Esc or clicking exits as today.

A receiver joining at any point gains rank on almost every captured frame:
repair rows are independent of each other and of the source rows with
overwhelming probability.

### 6.2 Downloadable GIF

`N` source frames followed by `R = ceil(gifRepairRatio · N)` repair frames
with r = 0 … R−1, `gifRepairRatio` = 0.25; R = 0 when N = 1. The stats
panel reports source and repair counts. A GIF shown in any viewer therefore
tolerates up to R misses per loop before the coupon-collector tail returns.

## 7. Decoder: RatelessAssembler

Replaces `FrameAssembler` on both sides (`web-app/cimbar.js`,
`android/lib/core/decode/frame_assembler.dart`); the acceptance rules of v2
§4.2 remain (RS failure, header validity, `fileId` change resets, `total`
mismatch rejects). State:

- `n` (from the first accepted frame), `fileId`, `encrypted`, `compressed`;
- `pivot[c]` for c ∈ [0, n): a reduced row (coefficients as `Uint8List(n)`
  with `coef[c] = 1` and zeros in columns < c, plus a 2104-byte body), or
  empty;
- `rank`; sets of seen source seqs and seen repair ids;
- counters for the debug log: source, repair, duplicate, dependent.

On an accepted frame:

1. Build the row (unit vector or generated coefficients; body as received).
2. Duplicate check: a source seq or repair id already seen → `duplicate`
   (rejected, rank unchanged).
3. Forward elimination: for c = 0 … n−1, if `coef[c] ≠ 0` and `pivot[c]`
   exists, row ← row − coef[c] · pivot[c] (GF multiply-add over the
   coefficient vector from column c and over the body).
4. Find the first non-zero column p. None → `dependent` (rank unchanged).
5. Scale the row by inverse(coef[p]) so `coef[p] = 1`, store as `pivot[p]`,
   rank += 1. A source frame whose seq is a free column reaches this step
   with p = seq and no arithmetic — the common, fast case.
6. When `rank == n`: back-substitute from column n−1 down to 0 so every
   pivot row becomes a unit vector; `bodies[i] = pivot[i].body`. Then
   `framedData()` = concatenation of the n bodies, as today.

Progress reported to the UI is `rank / n` (was `filled / total`). A frame
that fails RS is still rejected before any of this. Because a source frame
adds rank without arithmetic, a receiver that catches every frame of a small
file is exactly as fast as v2.

## 8. UI

Web app (all strings through `i18n.js`, all five languages):
- stats: frames = "N source + R repair"; bytes per frame unchanged;
  compressed size and ratio when bit 2 is set;
- frame-delay selector: when N > 100, a hint recommends 400 ms for phone
  capture;
- present mode: status line "source pass i / N" then "repair r"; the Esc
  hint as today.

Android:
- live scan progress "rank / N"; hints unchanged; the debug overlay line adds
  `rank=`, `rep=`, `dup=`, `dep=`;
- result card unchanged; `photo` path (single frame) unchanged — a
  single-frame file has no repair frames.

## 9. Testing

- **PRNG vectors**: JS and Dart both assert the §5.3 table from
  `spec/cimbar-v2.json`.
- **GF elimination**: for N ∈ {1, 2, 7, 64, 345}, generate N source bodies
  and 2N repair rows; any random subset of N rows that is full-rank decodes
  to the sources; repair-only receptions decode; duplicates and dependent
  rows leave rank unchanged; the systematic fast path is exercised
  (in-order source frames never touch the GF tables).
- **Compression**: a text file compresses and round-trips; random bytes are
  left uncompressed (bit 2 clear); compress-then-encrypt order verified by a
  golden.
- **Goldens** (`test-data/goldens/`, generated by `gen_goldens.js`): add
  `lorem_12k_coded` (compressed, 25 % repair frames), `lorem_12k_coded_enc`
  (compressed + encrypted) and keep every v2 golden. Sidecars record, per
  repair frame, the first 12 coefficients and the body hash. Dart's golden
  test decodes each GIF from (a) all frames, (b) source frames only, (c) a
  random drop of ⌊R⌋ frames including source frames.
- **Compatibility**: every v0.9.1 golden still decodes; a v2.1 GIF with bit 2
  clear decodes with the v2 assembler logic (source frames only).
- **Live scan**: controller test feeds mixed source/repair `FrameOutcome`s
  and asserts rank progress and completion; the synthetic camera test
  decodes a repair frame rendered by the JS encoder (golden).
- **Performance**: benchmark elimination at N=4096 (must stay under 100 ms
  per row on desktop JIT); present mode repair generation at N=345 under
  10 ms.

## 11. Expected effect

For the 345-frame case with p ≈ 0.5: from ~4000 frame slots (13 min, long
tail) to ~N·(1+ε)/p ≈ 700 slots (2.3 min, no tail). With deflate on a
typical document, N itself drops 2–5×. At 400 ms delay the phone catches
nearly every frame and a single systematic pass completes the transfer.

## 12. Risks and decisions

- **Old decoders and compressed files**: a v0.9.1 app shows "flags" for a
  compressed v2.1 GIF. Accepted; both apps update together.
- **Dense coding at the cap**: 25 MB of pivot rows at N=4096 is acceptable
  on target phones; sparse (LT/Raptor) coding is not needed at these sizes
  and would cost a far more complex decoder.
- **Present mode CPU**: generating repair bodies at 5 fps for N=4096 is
  ~8.6 M GF operations per frame (tens of ms in JS); acceptable, and the
  400 ms hint applies there anyway.
- **Repair-id wraparound** at 65536 restarts the same repair sequence; a
  receiver still gains rank from any not-yet-seen id, and a session that long
  (3.6 h at 200 ms) is not a real case.
- **No back-channel**: deliberately none; the rateless stream makes feedback
  unnecessary.

## 13. Implementation outline (for the plan)

1. Spec JSON + `format-data.js`; PRNG and GF helpers in `format.js` / a new
   `lib/core/format/rateless.dart`, with vector tests.
2. Compression in the container step (JS + Dart), flag bit 2, goldens.
3. `RatelessAssembler` (JS + Dart) with the §7 algorithm and the §9 tests;
   wire into `decodeRSFrame` consumers, GIF import, live scan.
4. Encoder: repair frame generation, GIF composition (N + R), present-mode
   canvas stream, UI strings.
5. Goldens regenerated (new coded goldens added, v2 goldens kept), docs,
   CHANGELOG, release v0.10.0.
